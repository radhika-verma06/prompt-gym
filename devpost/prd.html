The workspace, one loop

Left panel 42% — objective, criteria, editor, Run Tests. Right panel 58% — case cards, feedback, score, history. Score never lives on another page.
Arrival and orientation 10 seconds
  • Headline, one paragraph, three cards showing objective / difficulty / skill.
  • Flagship card marked “start here”.
  • Workspace shows objective, criteria and an example prompt before the first run.
  • No sign-in, no onboarding carousel.
The editor and Run Tests writing surface
  • Run Tests disabled until there's non-whitespace text, and it says why.
  • Running state; cannot be double-triggered.
  • Rerun keeps the previous attempt in history and keeps the current prompt in the editor.
  • The example prompt is collapsed by default so it can't be copied instead of understood.
  • No line-number gutter, no syntax highlighting — comfortable writing, not an IDE.
Test execution 6 cases, really run
  • All six cases hit the real model; nothing pre-determined, cached or fabricated.
  • Results land progressively, case by case.
  • Identical model and settings across attempts in a session.
  • Deterministic checks where the criterion allows (JSON validity, schema shape, forbidden content, numeric preservation).
  • A constrained judge only where no deterministic check exists, with its criterion stated on the case.
A case card failed · passed

Failed: status → criterion violated → observed behaviour in one plain sentence → constructive hint naming the behaviour to define → expandable raw model response.

Passed: status → what worked, briefly → same expandable raw response.

The hint never supplies a copy-ready instruction. The raw response is visible; the hidden input is not.
Regression detection observed vs inferred

Observed — always shown: the case that flipped, both verdicts with their attempt numbers, the difference in what the model actually did, and the prompt text that changed.

Inferred — labelled as inference: a possible explanation (added specificity, a narrower rule), offered only when the evidence supports it and phrased as a hypothesis. The app never asserts that overfitting caused the failure — with one run per attempt, causation isn't established.

When the evidence is thin, only the observation is shown and no cause is proposed at all.
Scan, focus and attempt diff experience
  • Compact row per case — state chip, name, criterion, one-line verdict; six rows fit one screen.
  • Rows expand in place; keyboard operable; Escape collapses.
  • Focus mode for a single failure, with score and prompt still visible.
  • Changes since attempt N names what the edit changed and every case that flipped.
Score, history, lesson and export motivation
  • Score out of six plus the delta from the previous attempt.
  • Progress chart across the session; best attempt marked.
  • Per-attempt improved / regressed summary.
  • Lesson statement derived from criteria actually met, not a canned line.
  • Export: Markdown by default, JSON available — includes a timestamp and the note that results came from real evaluations.

Also specified: first use, run in progress, completed run, model error (run-level, retryable, never a failed case, prompt preserved), empty history and session-only persistence.

Responsive: desktop is the target; narrow viewports stack with the score pinned above the case list, full-width rows, inline expansion, body text ≥16px, tap targets ≥44px, and no horizontal scrolling at 360px.

Accessibility: full keyboard operation with visible focus and a logical tab order; states differentiated by label, icon and border treatment, never colour alone; contrast ≥4.5:1; prefers-reduced-motion honoured; progress and each resolved case announced through a polite live region.

Building now

  • Landing with three packs; flagship fully realised, two simpler but polished
  • Six genuinely evaluated cases per pack, built on fair edge conditions
  • Split workspace, progressive results, four states, actionable feedback
  • Regression detection separating observed from inferred
  • Score, delta, chart, best attempt, lesson
  • Markdown + JSON export
  • A usable public deployment — key held server-side, per-session run cap

Not now

  • Adaptive hint coach — the static hint ships instead
  • More packs, difficulty tiers, cross-pack mastery
  • Accounts, saved history across sessions, shareable challenge links
Deployment is no longer deferred: presentation and a working product rank equally, so both are scheduled.

Non-goals

Not a chatbot, playground or prompt IDE · no prose-based prompt-engineering lessons · no arguable scoring · no multiplayer, leaderboards or social features · no server-side storage of prompts, no accounts, no database.

Two validator tiers, nothing else

Tier A — deterministic. JSON parses; schema and field types; required fields; no output value that appears nowhere in the input (fabrication check); amounts in an acceptable set; request counts.

Tier B — constrained judgement. Only where a criterion is genuinely interpretive. The judge sees the criterion, the input and the response — never the user's prompt — and returns pass | fail | uncertain against a fixed rubric, at the same fixed settings as the model under test.

Score arithmetic

  • A case is scored, unscored (uncertain) or unresolved (API errored).
  • Headline reads 4 of 5 scored · 1 uncertain · 0 errors.
  • Uncertain and errored cases leave the denominator. A technical error can never lower the score.
  • Delta only compares attempts with matching scored counts — otherwise it says not directly comparable.
  • Best attempt is the highest passed / scored, shown with its scored count.
Keeping the hidden tests hidden leak channels

The raw model response is shown because it is the evidence — which makes it the most likely leak channel.

  • Responses are length-capped and rendered as inert text.
  • Every case gets an echo-risk review: if a response would reproduce the input or disclose an acceptable answer, it is redacted with “response withheld to protect this case” plus the behavioural description.
  • Expected values never appear in feedback, hints, diffs, tooltips or the export — feedback describes behaviour, not the answer.
  • Attempt comparison shows changes to the user's prompt, never hidden inputs.
  • Case rows, URLs, HTML attributes and page source carry no hidden input text.
Transparency in the product itself: every case shows which validator decided it, and the export records the model, the fixed settings, the timestamp and the known limits — a judge can be inconsistent, a provider can vary between identical runs, and uncertainty is reported rather than quietly resolved.

Blocking the spec

  • Which model API, whose key — latency, cost and reproducibility all follow from it. Blocks `4-spec`.
  • Judge calibration — which Tier B verdicts are stable enough to ship, and when a judge must return uncertain instead of guessing.
  • Where it deploys, how the key is held — server-side route required; host and per-session run cap are `4-spec` decisions.
  • Export delivery: clipboard, download, or both — can wait.
  • Whether a real, unassisted regression appears with these six cases — verified by running the demo prompts for real during build. Never engineered.
