Structured Extraction Attempt 4
6 cases · inputs hidden

Objective

Convert each incoming customer message into strict JSON with fields order_id, reason, amount_usd and wants_replacement. If a value isn't present, mark it unknown — never guess it.

Success criteria

  • C1Output always parses as valid JSON
  • C2Exactly the four required fields, correct types
  • C3Missing values marked unknown, never invented
  • C4Amounts preserved exactly, as numbers
  • C5Ambiguous references handled without fabrication
  • C6Two requests in one message both captured

Your prompt

Extract the order details from the message as JSON with these keys: order_id, reason, amount_usd, wants_replacement. Rules: - Keep any order identifier exactly as written. - Always take the number that follows a dollar sign. - If a value is missing, mark it unknown instead of guessing.

Observed

Your edit changed one rule: “the number that appears after the dollar sign” became “always take the number that follows a dollar sign.” Case 3's message contains two amounts — a delivery fee and the refund the customer is asking for. Attempt 3's response reported the refund; attempt 4's response reported the fee. Everything else about your prompt is unchanged.

Possible explanation — not established

The stronger wording (“always”) may have narrowed the model's choice to the first number it sees rather than the one that means “refund”. That would cost generality on any message with more than one amount.

This is an inference from a single pair of runs. The app states what changed and what it plausibly cost — it never claims the change caused the failure.
