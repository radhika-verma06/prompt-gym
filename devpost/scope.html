Prompt Gym

A practice gym for writing prompts. Pick a challenge, write a prompt, run it against hidden cases — and watch your score rise, or fall.

The kernel

The overfitting trap

You fix one failing case with an overly specific instruction. A case that used to pass breaks. The app highlights the regression, shows what changed, and explains that you optimised for one scenario instead of writing something that generalises.

That “wait, my score went down?” moment is the product. Delete it and this is a generic prompt linter.

And it has to be honest

The trap emerges from test cases that are diverse but consistently specified — not contradictory requirements, not hidden gotchas, not scoring that shifts to manufacture a lesson.

A user who writes a genuinely general prompt reaches 6/6. Anything less makes the lesson a trick.

The demo’s 3/6 → 5/6 → 4/6 → 6/6 is illustrative. No scoring path may be tuned to reproduce it.

Journey, loop and boundary

Every result on this path comes from a real evaluation. If a case can’t be judged reliably, it is shown as uncertain — never counted as a failure, never counted as a pass to protect a number.

The repetition

Pick a pack → read the objective and criteria → write → run → read what actually broke → edit → rerun.

They come back because the next attempt is a hypothesis, not a repeat.

What has to be true each time

  • Hidden inputs, visible model responses — memorising has to be harder than learning.
  • Same model, same settings: a score change means the prompt changed.
  • Feedback names the behaviour, not the vibe.
  • Regressions are surfaced, not buried in the score.

In scope — the whole proof of concept now
  • Three packs: structured extraction · rules under customer requests · rewriting without losing information.
  • Depth over breadth: one exceptional pack plus two simpler polished ones beats three unreliable experiences.
  • One editor, one workspace, six cases per pack.
  • Visible objective, criteria and a good-prompt example on first arrival.
  • Actionable per-case feedback; real model responses; hidden inputs.
  • Score history and regression detection with attempt comparison.
  • Export as clean Markdown or JSON: prompt, results, history, lessons.
Later — wanted, not now after the loop works
  • The hint coach: “try defining how the model should handle missing information” — never a finished prompt.
  • More packs and difficulty tiers; personal best, iteration count, principles summary.
  • A public deployment — strengthens the submission, but only after the product works and the demo is excellent.
Cut — and why named, not silent
  • Auth and accounts — no identity needed to prove the loop.
  • Database — history needs to survive the session and the export, nothing more.
  • Feed, leaderboards, XP, profiles — none of it teaches prompting.
  • A large challenge library — three deep packs beat fifteen shallow ones; depth is where the trap lives.
  • Extra integrations — the model call and the export are the whole system.

Open questions handed to the spec

  • Real execution means a real model API — provider, model, key ownership, cost per demo run. Biggest schedule risk.
  • Trustworthy scoring — which checks are deterministic, where a constrained judge is genuinely needed, how uncertainty is displayed.
  • Stable comparisons — fixed settings so a delta means a prompt change, not the dice.
  • Engineering the trap honestly — diverse but consistently specified cases; not contradictory requirements, not a switch.
  • Ten-second orientation — example, criteria and objective fitting one screen without crowding the editor.
