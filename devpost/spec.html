Prompt Gym — how it's built

Two screens, one hidden worker, no database. The whole architecture exists to keep the hidden tests on the server and the scoring honest.

The two decisions that shape everything

Hidden inputs never reach the browser

Production fixtures arrive from deployment configuration, not from the repository. The browser sends only your prompt; the server pairs it with each hidden input and returns a description of what happened.

Not in the page, not in a response body, not in DevTools — and not in the public repo either.

The repo ships labelled sample fixtures so a clone runs without secrets; the workspace shows a “sample fixtures” badge whenever they're in use.

Rules decide, judgement is the exception

Five of the six flagship criteria are checked by code: valid JSON, exact fields and types, no invented values, amounts in an acceptable set, request counts.

One criterion is interpretive and goes to a judge model — which never sees your prompt, only the criterion, the input and the response.

A malformed judge verdict becomes uncertain, never a failure. An API error leaves the denominator entirely.

Architecture

The dashed green arrow is the whole point: what comes back is a verdict, a one-sentence observation and a redacted response. No inputs, no expected answers — so nothing in the browser can disclose a case.

What happens when you press Run Tests

  1. You press Run Tests.
  2. The browser sends { packId, prompt } to /api/run — your prompt and nothing else.
  3. The server looks up the pack and pairs your prompt with each hidden case input, three at a time.
  4. Each response goes to its validator — rules for five criteria, the judge for one.
  5. The echo-risk check compares each response against the case's input and acceptable answers, redacting when needed.
  6. Cases stream back as they resolve, with state, tier, observation and redacted response.
  7. The score arithmetic runs: passed / scored, with uncertain and errored counted separately.
  8. This attempt is compared with the previous one — flips are observed, explanations are only inferred when the evidence qualifies.
  9. The attempt is written to sessionStorage, and the chart, changes panel and lesson update.
Pack content lib/packs/
  • Static TypeScript: three packs, six criteria (C1–C6) each, six cases each.
  • A case carries its hidden input, acceptable answers, criterion IDs and validator.
  • Ships in the bundle, but only server code reads input and acceptable.
Run route app/api/run/route.ts
  • The only endpoint. Validates the request with Zod, resolves the pack server-side.
  • Runs six cases at concurrency 3, streams results as they resolve.
  • Never returns an input or an acceptable answer.
Model client and frozen settings lib/model/
  • One place the provider is called; OpenAI-compatible base URL so the provider is an env var.
  • Frozen per session: model IDs, temperature: 0, max tokens, wrapperVersion.
  • Every attempt records them, so a score change is attributable to the prompt.
Validators lib/validators/

TIER A JSON parses · exact fields and types · required fields · no fabricated values · amounts in acceptable set · request counts.

TIER B One criterion. Receives criterion + input + response, never the prompt. Returns {verdict, reason}, validated with Zod; unusable output → uncertain.

Redaction lib/redact.ts
  • Length-cap every response; render as inert text.
  • Compare against the case input and acceptable answers, normalised, to catch quotes and reformats.
  • On a match: substitute the withheld marker plus a behavioural description.
Scoring and regression lib/scoring.ts · lib/regression.ts
  • passed / scored; uncertain and unresolved excluded from the denominator.
  • Delta and best attempt only compare matching scored counts.
  • Regression returns observations always, inference only past a written evidence threshold.
Attempt store and export lib/attempts.ts · lib/export/
  • Attempts in sessionStorage, capped at 20; nothing server-side.
  • Markdown by default, JSON available; records model, settings and timestamp.
  • Contains only what was already on screen.

Where it will break, and what you see

  • Rate limit or timeout mid-run → run marked incomplete, those cases unresolved, Retry offered, prompt untouched.
  • Judge returns junk → case becomes uncertain with the reason, out of the denominator.
  • No API key → "evaluation isn't configured" with setup steps, not a 500.
  • Response would disclose its case → withheld marker; the verdict still stands.
  • Two identical runs disagree → both kept, disagreement shown, judge-based verdicts labelled as the variable part.

What was simplified, and why

  • sessionStorage instead of a database and accounts — the loop and the export are the product.
  • One judged criterion in the flagship, not a judge per case — credibility and cost.
  • Pack content in code, not a CMS — three packs don't need authoring.
  • A versioned wrapper instead of a prompt-templating DSL.
  • Concurrency 3 instead of all six at once — keeps the free tier's tokens-per-minute comfortable.

The five refinements, as built

1 · Public vs private fixtures

Public metadata (objective, criteria, difficulty) ships in the repo. Fixtures — inputs and acceptable answers — come from PACK_FIXTURES_JSON at deploy time and are parsed with Zod at boot. Sample sets are committed, labelled in the UI.

2 · Fair evaluation

No JSON mode on the model under test — the constraint belongs in the user's prompt. Structured output only for the judge. Per-criterion pass/fail rules are written down, including the fabrication allowlist.

3 · Comparable attempts only

A delta requires matching model IDs, settingsHash, evaluationVersion, fixtureSetId and scored count. Otherwise: “not directly comparable”, with the reason. Inference is typed separately from observation.

4 · Proportional redaction

Withhold on a real disclosure — a distinctive span of the input, or an acceptable answer the user couldn't have derived. A correct response stays visible. Residual risk documented.

5 · Server-side protection: prompt bounds 40–4,000 characters · body cap 16 KB · 20 s per call, 45 s per run · 3 cases in flight · 6 runs/min and 40/hour per IP · shared daily budget of 900 model calls (~128 runs). Counters live in Upstash Redis when configured, else in memory — and the README says which guarantee is actually in force.
